# VetCrew Simulation Core — Architecture Doctrine

VetCrew is a crew simulation trainer for veterinary ER/ICU staff: a shared simulation core, role-specific stations (each trainee sees only their role's view), an instructor station that can inject events live, and after-action review (AAR). It's used for two things — pre-hire/onboarding readiness assessment ("is this person ready for the floor") and refresher training for veteran staff. That second use case (a hiring/competency signal) means the architecture has to produce an *auditable, replayable* record of what happened, not just a live experience.

This doctrine is a proposed starting point, not yet battle-tested against a real build. Revisit it after the first playable prototype — but until then, treat it as the default so early decisions don't fragment across sessions.

## Why this needs its own doctrine (not VetTrack's)

VetTrack uses SSE/outbox for equipment-status fan-out — one-directional, server-to-client, tolerant of seconds of latency. VetCrew is different: the instructor needs to push events to trainees *and* trainees' actions need to reach the sim engine, both with sub-second latency, because the whole point is simulating time pressure. **Default to WebSockets for the live session channel**, not SSE. Don't carry the SSE/outbox pattern over just for consistency with VetTrack — it's solving a different problem.

## Core entities

| Entity | What it is |
|---|---|
| `Scenario` | Versioned scenario definition (see `vetcrew-scenario-authoring`) — the template a session is run from |
| `SimSession` | One live run of a scenario, with a `session_id`, a status, and a set of connected role stations |
| `RoleStation` | A connection bound to one role within one session (e.g. "primary tech" in session X) |
| `InjectionEvent` | An instructor-triggered event during a live session (complication, new info, equipment failure) |
| `ActionEvent` | Something a trainee did, timestamped and attributed to their role |
| `TelemetryFrame` | A periodic snapshot of patient state (vitals) — derived, not authoritative |
| `AARRecord` | Post-session artifact derived from the event log + scores, not stored separately as its own truth |

## Doctrine: one authoritative engine, thin clients

A single Sim Engine process owns canonical state for a `SimSession` — patient vitals, scenario progress, which injections have fired. Role stations and the instructor console are thin clients: they render what the engine pushes them and send intents (actions, injection requests) back, but never compute session state locally.

**Why this matters more here than in most real-time apps:** the training value of VetCrew depends on every role seeing a *consistent* shared reality — that's what teaches closed-loop communication and shared situational awareness. If two role stations could independently drift on "what the current heart rate is" due to client-side prediction or stale reconnect state, the tool would be teaching the wrong lesson. Correctness of shared state is the product, not just an engineering nicety.

## Doctrine: event-sourced AAR, not derived-state AAR

Every injection, trainee action, and vitals tick is an immutable, timestamped, role-attributed event appended to a session's event log. The AAR is generated by deterministic replay of that log — not by snapshotting some mutable "current state" table at the end. This gives you:

- **Scrubbable replay** for the AAR viewer (jump to any point, reconstruct state up to that point)
- **Auditability** for the hiring-readiness use case — if a readiness score is ever challenged, you can point to the exact events that produced it (see `vetcrew-readiness-scoring`)
- **A natural source for scoring signals** (e.g. time-to-first-intervention is just a query over the event log, not a separately-tracked field you have to remember to update)

Don't optimize this away early by storing only aggregated results. The aggregation can always be rebuilt from the log; the reverse isn't true.

## Session lifecycle

```
draft → briefing → running ⇄ paused → debrief → scored → archived
```

- **draft**: scenario selected, roles not yet assigned/connected
- **briefing**: role stations connected, pre-scenario context shown, session not yet live
- **running ⇄ paused**: instructor can pause at any point (freezes engine ticks, doesn't discard state) and resume
- **debrief**: session ended, AAR available, not yet scored
- **scored**: readiness/refresher scores attached
- **archived**: retained for audit/trend history (see refresher-drift detection in `vetcrew-readiness-scoring`)

Instructor-only actions: pause/resume, inject, end session. Trainee actions: everything else, always attributed to a role.

## Reconnect handling

Role stations *will* drop connection mid-session (hospital wifi, a trainee's tablet locking). On reconnect: replay the last-N events plus a fresh full snapshot of current state, not the entire session history — the client needs "where are we now," not a full re-derivation. Show an explicit "reconnecting" state rather than rendering stale last-known values; a trainee acting on stale vitals is a training-integrity bug, not just a UX rough edge.

## Concurrency

Multiple crews can train simultaneously — each `SimSession` is independent and scoped by `session_id`; there's no cross-session shared state. Don't assume one engine instance total; assume one logical engine *per active session*, however that's implemented (separate processes, or a single process multiplexing sessions by ID — pick based on expected concurrent-session count once that's known, not upfront).

## Open questions to revisit

- Backend stack: not yet decided whether VetCrew reuses VetTrack's Express/Drizzle/Postgres/Redis stack or is a clean-slate choice. Reusing it lowers cognitive load for a solo AI-agent-driven build; a clean slate avoids carrying over assumptions (like SSE/outbox) that don't fit. Decide explicitly, don't default silently.
- Where does the Sim Engine run relative to hospital network conditions — LAN-local for latency, or cloud with graceful degradation? This affects the WebSocket-vs-polling fallback story.
- At what point does instructor-injection get a scripting/rules layer (conditional injections) vs staying purely manual-trigger? Keep it manual-trigger until there's evidence instructors want more.
